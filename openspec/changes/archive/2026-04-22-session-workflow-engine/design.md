## Context

### Current state

- 当前会话入口以 `businessRequest` 自由文本为主，前端主要字段位于 `standalone/web/index.html` 与 `standalone/web/app.js`。
- 后端会话创建与推进逻辑集中在 `standalone/MappingServer.java`，阶段步骤由静态模板驱动，推进规则偏线性。
- 阶段展示侧重“步骤清单 + 聊天消息 + 推荐结果”，缺少显式的“已确认事实/关键缺口/下一步建议”解释信息。

### Target state

- 会话入口升级为“自由文本 + 结构化上下文”混合模型，且保持老请求兼容。
- 阶段引擎支持“必答步骤 + 条件分支步骤 + 完成判定”，信息不足时不推进而是追问。
- 会话查询响应支持阶段解释性字段，前端可渲染五段式解释视图（目标、事实、缺口、建议、未决项）。

## Goals / Non-Goals

**Goals:**

- 在不破坏现有主流程的前提下增强输入灵活度与澄清细粒度。
- 将阶段推进从“固定问答”提升为“可分支、可判定”的交互引擎。
- 提升阶段输出可解释性，帮助业务用户理解“系统为什么这样问”。
- 为后续 spring 模式对齐建立稳定契约。

**Non-Goals:**

- 不重写推荐引擎评分算法与映射数据结构。
- 不引入新的外部存储组件（如 Redis、消息队列）。
- 不在本次内完成 spring 与 standalone 全量实现统一，仅先定义行为契约。

## Decisions

### Decision 1: 采用向后兼容的混合输入模型

- 方案：保留 `businessRequest` 必填语义，新增可选 `contextProfile`（或等价结构）字段，承载目标、时限、角色、约束等结构化信息。
- 理由：最小化 API 破坏风险，同时让引擎可直接消费结构化语义。
- 备选方案：
  - 仅增强 prompt 解析自由文本：实现快，但稳定性弱、可观测性差。
  - 强制全面结构化表单：信息质量高，但对现有调用方破坏大。

### Decision 2: 引入步骤完成判定层

- 方案：在每个步骤增加“最小信息要求”判定，未满足时保持 `CURRENT` 并生成补充追问。
- 理由：解决“用户一句话即推进”的粗粒度问题，提升阶段信息完整度。
- 备选方案：
  - 维持现状线性推进：实现简单，但澄清质量不稳定。
  - 完全交由 LLM 判定：灵活但可控性和一致性不足。

### Decision 3: 阶段解释信息作为会话响应扩展字段

- 方案：在会话详情响应中增加阶段解释结构（目标、已确认事实、关键缺口、下一步建议、未决项）。
- 理由：后端统一生成语义，前端仅负责展示，便于多端复用与测试。
- 备选方案：
  - 前端根据消息自行总结：前端复杂度高且一致性差。
  - 仅在 UI 端提示不改接口：难以复用到其他客户端。

### Decision 4: 环境变量与降级行为保持现有约束

- 方案：继续以 `OPENROUTER_API_KEY` 控制 AI 增强开关；未配置时走规则化追问与总结。
- 理由：符合当前部署模型，避免新增配置成本。
- 备选方案：
  - 新增多模型路由配置：灵活但超出当前变更范围。

## Risks / Trade-offs

- [输入字段扩展造成前后端不一致] → 通过默认值和字段可选策略保证兼容，并补充契约测试。
- [动态分支导致流程复杂度提升] → 采用“核心必答优先，条件分支渐进启用”的策略。
- [解释字段过多影响响应体大小] → 先输出摘要级字段，详细内容按需扩展。
- [无 API key 时文案质量下降] → 保留模板化 fallback，并记录后续优化点。

## Migration Plan

1. 在 change specs 中明确新增与修改需求，冻结契约。
2. 后端先实现请求/响应字段扩展（保持向后兼容）。
3. 引入步骤完成判定与条件分支编排，先覆盖高价值阶段。
4. 增加阶段解释字段并完成前端渲染。
5. 回归验证：旧请求不带结构化字段仍可完整跑通。

Rollback strategy:

- 若动态分支逻辑出现异常，可切回仅必答步骤模式（特性开关或条件短路）。
- 若解释字段导致前端异常，可暂时隐藏新展示区并保留旧界面。
