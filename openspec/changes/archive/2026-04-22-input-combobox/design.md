## Context

### Current state

- 当前输入控件以纯文本框为主，字段定义分散在 `standalone/web/index.html` 与 `standalone/web/app.js`。
- 会话启动参数由 `standalone/MappingServer.java` 解析，支持自由输入但缺少标准化选项约束。
- 输入值可通过草稿恢复，但不同用户输入同义词或噪声表达时，后端上下文识别稳定性下降。

### Target state

- 关键输入字段统一支持“下拉选择 + 手动输入”双模式。
- 前端统一管理字段模式（选择/手输）、默认选项、切换与草稿恢复行为。
- 后端保持 API 向后兼容，新增字段输入可选，且对选项值与自定义值做统一规范化处理。

## Goals / Non-Goals

**Goals:**

- 在不破坏既有流程的前提下提升录入效率与输入一致性。
- 降低用户对可选值的记忆成本，减少无效输入导致的澄清往返。
- 让标准化选项值与自定义值都能被后端稳定消费。
- 为后续多端（Standalone/Spring）一致的输入规范奠定基础。

**Non-Goals:**

- 不引入外部字典服务或动态配置中心。
- 不在本次变更中重构推荐引擎或方法论评分逻辑。
- 不要求所有现有字段一次性完成复杂校验，仅先覆盖关键输入字段。

## Decisions

### Decision 1: 输入控件采用“可编辑组合框”模式

- 方案：每个关键字段提供预置选项（下拉）与手动输入入口，用户可随时切换。
- 理由：兼顾效率（常见值直选）与灵活性（异常值手输）。
- 备选方案：
  - 全部改为下拉：一致性高，但表达受限。
  - 全部保留文本框：灵活但标准化不足。

### Decision 2: 前端维护统一字段元数据

- 方案：在 `app.js` 定义字段配置（选项列表、默认模式、序列化 key），驱动渲染与状态保存。
- 理由：减少模板与逻辑分叉，便于后续新增字段。
- 备选方案：
  - 在 HTML 硬编码每个字段：短期快，长期维护成本高。

### Decision 3: 后端做轻量规范化并保持兼容

- 方案：后端对输入执行 trim、空值剔除、基础映射规范化；旧字段路径继续可用。
- 理由：不要求前端强依赖特定格式，降低调用方升级成本。
- 备选方案：
  - 强制仅接受枚举值：标准化强，但破坏兼容性和业务灵活输入。

### Decision 4: 失败与回退策略保持渐进

- 方案：字段配置缺失时回退到纯文本输入；解析异常时降级为原始字符串处理并记录告警。
- 理由：保证交互可用性优先，避免因配置问题阻塞会话创建。
- 环境变量影响：可选增加开关（如 `INPUT_COMBOBOX_ENABLED`）控制是否启用双模式输入。

## Risks / Trade-offs

- [选项维护成本上升] → 采用集中字段配置并限定首批关键字段范围。
- [手动输入仍可能产生噪声] → 后端增加轻量规范化与缺口追问协同。
- [模式切换引发用户困惑] → 在 UI 显示当前模式与“可切换”提示文案。
- [兼容逻辑增加代码复杂度] → 通过字段元数据驱动与统一序列化函数降低重复实现。

## Migration Plan

1. 先在变更 specs 中明确双模式输入行为与兼容语义。
2. 实现前端字段元数据与组合框渲染，保留旧请求字段路径。
3. 后端补充输入规范化，确保旧请求与新请求并存。
4. 回归验证：纯文本旧模式、下拉模式、手动输入模式均可创建会话。
5. 若出现问题，临时关闭双模式开关并回退到纯文本展示。
