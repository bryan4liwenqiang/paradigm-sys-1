# session-workflow-engine

## Purpose

定义会话驱动的阶段化需求澄清引擎行为，包括会话创建、步骤推进、阶段完成、阶段刷新、消息记录与持久化恢复。
## Requirements
### Requirement: 会话创建与初始状态
系统 MUST 支持创建新会话，并在创建后初始化阶段工作流、首个步骤状态与首条 assistant 引导消息。系统 MUST 支持“自由文本 + 结构化上下文”的会话初始化方式。系统 MUST 正确消费来自“下拉选择 + 手动输入”双模式控件的输入值。

#### Scenario: 创建会话成功（混合输入）
- **WHEN** 调用 `POST /api/v1/sessions/start` 且提供 `businessRequest` 与结构化上下文
- **THEN** 返回 200 与唯一 `sessionId`
- **AND** 当前阶段为首阶段且首个步骤状态为 `CURRENT`
- **AND** 会话上下文中可读取结构化字段

#### Scenario: 缺少 businessRequest
- **WHEN** `businessRequest` 缺失或为空
- **THEN** 返回 400
- **AND** 提示必填约束

#### Scenario: 双模式输入驱动会话初始化
- **WHEN** 前端通过双模式控件提交启动请求
- **THEN** 会话引擎应按统一字段语义初始化上下文
- **AND** 后续阶段步骤推进不依赖字段来源模式

### Requirement: 步骤推进状态机
系统 MUST 在用户提交消息后推进当前步骤状态，并保持 `CURRENT/PENDING/DONE` 状态转换可追踪且可重建。系统 MUST 在信息不足时保持当前步骤并继续追问，不得直接推进。

#### Scenario: 正常推进一步
- **WHEN** 当前步骤存在且用户提交信息满足步骤最小要求
- **THEN** 当前步骤标记为 `DONE`
- **AND** 下一步骤标记为 `CURRENT`
- **AND** 写入 assistant 下一步追问消息

#### Scenario: 信息不足不推进
- **WHEN** 用户回复未满足当前步骤最小信息要求
- **THEN** 当前步骤保持 `CURRENT`
- **AND** assistant 生成针对缺口的补充问题

#### Scenario: 当前阶段最后一步完成
- **WHEN** 用户完成当前阶段最后一个步骤
- **THEN** 系统生成阶段总结
- **AND** 自动推进到下一阶段并发出阶段切换提示

### Requirement: 阶段刷新行为
系统 MUST 支持针对指定阶段刷新当前步骤关注点，并将刷新结果纳入消息历史。

#### Scenario: 刷新当前步骤问题
- **WHEN** 调用阶段刷新接口且阶段有效
- **THEN** 当前步骤问题可被更新为新的引导问题
- **AND** 消息历史中出现刷新确认消息

### Requirement: 消息与会话可追溯
系统 MUST 按时间顺序保存用户与 assistant 消息，并在查询会话时返回完整上下文。系统 MUST 返回当前阶段的解释性信息，支持前端展示“目标、事实、缺口、建议”。

#### Scenario: 查询会话详情
- **WHEN** 调用会话查询接口
- **THEN** 返回当前阶段、阶段明细、步骤状态与消息列表
- **AND** 消息条目包含角色、内容与时间戳
- **AND** 返回可展示的阶段解释字段

### Requirement: 持久化与恢复
系统 MUST 支持会话状态持久化并在服务重启后恢复，避免已进行中的需求澄清流程丢失。

#### Scenario: 重启后恢复
- **WHEN** 服务在已有会话状态下重启
- **THEN** 先前会话可继续查询与推进
- **AND** 阶段与步骤状态保持一致

### Requirement: AI 增强的可降级性
系统 MUST 在未配置 AI 能力时保持核心流程可用，并提供可理解的回退提示文本。

#### Scenario: 未配置 OpenRouter
- **WHEN** 环境未配置 `OPENROUTER_API_KEY`
- **THEN** 会话创建、推进、总结等核心流程仍可执行
- **AND** assistant 输出回退到规则化文本

### Requirement: 输入建模与上下文画像
系统 MUST 支持“自由文本业务诉求 + 结构化上下文字段”的混合输入模型，并在会话中持续维护该上下文画像。

#### Scenario: 创建会话时提交结构化上下文
- **WHEN** 调用 `POST /api/v1/sessions/start` 时提供目标、时限、角色、合规等级等结构化字段
- **THEN** 系统保存结构化字段并与 `businessRequest` 一并作为会话上下文
- **AND** 后续阶段问题生成可引用该上下文

#### Scenario: 结构化字段缺省
- **WHEN** 创建会话时未提供部分结构化字段
- **THEN** 系统仍可创建会话
- **AND** 在后续互动中优先追问缺失字段

### Requirement: 动态步骤编排与完成判定
系统 MUST 支持“必答步骤 + 条件分支步骤”的动态编排，并基于信息完整度判定是否推进到下一步骤或继续追问。

#### Scenario: 触发条件分支步骤
- **WHEN** 会话上下文满足某条件（如高合规等级、紧时限、多角色审批）
- **THEN** 系统将对应分支步骤插入当前阶段流程
- **AND** 分支步骤状态与主步骤状态统一纳入工作流追踪

#### Scenario: 信息不足不推进
- **WHEN** 用户回复未满足当前步骤最小信息要求
- **THEN** 系统保持当前步骤为 `CURRENT`
- **AND** assistant 生成针对该缺口的澄清追问

### Requirement: 阶段解释性展示
系统 MUST 在阶段视图中提供可解释信息，至少包括阶段目标、已确认事实、关键缺口与下一步建议。

#### Scenario: 返回阶段解释信息
- **WHEN** 查询会话详情或完成一次消息推进
- **THEN** 响应可包含该阶段的解释性字段
- **AND** 前端可据此展示“为何提问、缺口是什么、建议下一步是什么”

#### Scenario: 阶段完成解释
- **WHEN** 某阶段完成并切换到下一阶段
- **THEN** 系统输出该阶段完成摘要与未决项
- **AND** 明确下一阶段的关注重点
